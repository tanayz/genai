Memory for agents that must not forget,
and must not guess.

This guide explains how to give an AI assistant a durable memory of every conversation it has had with a customer, how to connect that memory to the agent so that it recalls and saves facts without being asked, how to measure whether the memory is actually working, and how to decide, against written criteria, whether it is safe to release. It is written for engineers who are new to agent memory and want to end at production depth. 01foundations

Three things people call memory

An AI agent, at its simplest, is a language model plus the list of messages exchanged so far. That list is the agent's entire knowledge of the conversation, and when the request ends, the list is discarded. Everything people mean by "giving the agent memory" comes down to keeping some of that information alive for longer. The difficulty is that the word memory is used for three different things, each with a different lifetime, and each one is solved by a different tool. Confusing them is the most common reason memory projects disappoint, so this guide starts by taking them apart.

Working memory is the current conversation. Every time the model answers, the whole transcript so far is sent to it again, so the cost of each turn grows with the length of the conversation. Agent frameworks manage this with a conversation manager that trims or summarises the oldest messages, and that trimming is exactly the moment at which facts disappear. Session memory persists the transcript to disk or to a store such as Amazon S3, so that a conversation interrupted by a dropped call or a restarted process can resume where it left off. It is valuable, but it is still a transcript: two sessions know nothing about each other, and answering a question about last June's call would mean loading the whole of it. Long-term memory is different in kind. Instead of messages it stores facts, distilled from conversations by a model, and those facts belong to the customer rather than to any single conversation. That is what mem0 provides, and it is the subject of the rest of this guide.

The design decision that matters most is whose memory a fact belongs to. mem0 attaches every fact to a scope. Facts stored under a user_id are about the customer and follow the customer across every conversation and channel. Facts stored under an agent_id are things the assistant has learned about doing its own job, and follow the agent across customers. Facts stored under a run_id matter only within one conversation and can be discarded afterwards. Choose these scopes deliberately at the start: customer isolation, retrieval quality and governance all rest on them, and they are hard to change once data has been stored.
02how mem0 works

From transcript to facts, and back

mem0 does one job and does it well. Given a conversation, it uses a single model call to extract a small set of facts, each written so that it makes sense on its own. It converts each fact into an embedding, a numeric representation in which similar meanings sit close together, and stores the fact together with its embedding and any metadata you attach, such as the channel or the date. When the agent later needs to know something, mem0 embeds the question in the same way and returns the few stored facts whose meaning is closest to it. Every component in this pipeline is one you choose: the extraction model, the embedding model and the vector store. In this guide all three run on AWS Bedrock, with FAISS as a local vector store during development and Amazon OpenSearch in production.

What the extractor does well

The extractor writes facts that stand on their own, so that "Priya's EFTPOS terminal at the depot was dropping out" is stored rather than "it kept dropping out", which would be meaningless a month later. It resolves relative expressions such as "by Thursday" into absolute dates. And it extracts from the banker's side of the conversation as well as the customer's, which matters in banking because the promise a banker makes during a call is often the single most important fact to remember. On the 7 conversations in the example it produced 34 facts from 58 messages, taking about 8 seconds per conversation and up to 10.

What it does not do

The open-source 2.x release of mem0 only ever adds facts; it never updates or deletes an existing one on its own. When the customer changes her contact preference, the store ends up holding both the old preference and the new one. Retrieval usually ranks the newer fact first, because the extractor phrases a change as a change, but nothing marks the old fact as history, and a differently worded question can surface it first. Keeping memory true over time is therefore a responsibility of the application that uses mem0, not of the library. Section 06 shows how to carry that responsibility with a reconciliation step and an audit trail.

Two API details that break most published tutorials. Since version 2.x, search() and get_all() take the scope inside a filters argument, as filters={"user_id": ...}, and reject the older top-level user_id parameter. The memory tool shipped with the strands-agents-tools package still uses the old form, so its retrieve and list actions fail against current mem0. Second, the open-source library has no way to tell the extractor when a conversation took place, so it resolves "last Friday" against today's date. When you ingest historical transcripts, write the conversation date into the text itself.
03integration

Who decides to remember: the model or the framework?

Calling mem0 by hand, as the previous section did, is fine for understanding it, but a real assistant cannot depend on someone remembering to make the call. Recall and saving have to happen as a natural part of every conversation. The question that shapes the design is who decides when that happens: the language model, by choosing to call a tool, or the framework, by doing it automatically around every turn. There are three workable answers, shown below. They differ in how much control you keep, what each turn costs, and how each one fails.

The table summarises the trade-offs. "Tenant isolation" means the way the customer's identity is fixed so that the model can never choose to read a different customer's memory. In patterns A and B the identity is fixed inside the function that creates the tools or hooks (a closure, in programming terms), so the model receives tools that already know which customer they serve; in pattern C it is passed to the store when the store is constructed. "Durable history" is the transcript the framework keeps between turns.

Three rules hold whichever pattern you choose. First, bind the customer's identity at the point where the tools or the store are created, never as a parameter the model fills in. A prompt injection cannot read another customer's memory if there is no parameter through which to name that customer. Second, inject recalled facts ephemerally, meaning for one model call only. Anything written into the durable transcript is re-sent to the model on every later turn and, worse, is saved back into memory by the next extraction, which creates a feedback loop of memories about memories. Third, save in the background. Extraction takes seconds, and the customer waiting on the phone gains nothing from it.

The Context Pack

All of this machinery exists to produce one artefact. Before a banker picks up a call, the assistant hands them a short brief generated from memory: who the customer is, what they most likely want, what the bank still owes them, how they prefer to be treated, and what must not be got wrong. The brief has a fixed shape, so downstream systems can rely on it, and every line carries the identifiers of the memories it was built from, so a banker can check any statement against its source. 04evaluation

Where memory fails, measured one layer at a time

An assistant that answers a handful of questions well in a demo is not evidence that it will answer well in production. Before memory is allowed to shape what a banker says to a customer, three questions need numerical answers. Is the assistant better with memory than without it, and how close does it get to the best possible result, which is having every transcript in front of the model? When it is wrong, where in the pipeline did it go wrong? And what does being right cost in time and tokens? A single accuracy score answers the first question at best. It says nothing about the second, and the second is the one an engineer needs in order to know what to fix.

The dataset

A good memory test set is built the way the public benchmarks are built. LOCOMO and LongMemEval, two widely used research benchmarks for conversational memory, both consist of long, dated, multi-session conversations, and both record which turns hold the evidence for each answer, which is what makes it possible to measure retrieval separately from answering. Ours follows that recipe at a size that keeps the notebooks cheap to run. It has two business customers whose facts are deliberately similar in shape, so that a test for information leaking between customers means something, and 24 questions of the kind a banker would ask, in five categories that map to the five abilities LongMemEval identifies. Every gold answer was checked against the 2026 calendar. The conversations are listed below in date order.

The judge

The answers are graded by a language model acting as a judge, and four design choices make that grading trustworthy. The judge is a stronger model than the one under test, so Claude Sonnet grades what Claude Haiku answered and does not share its blind spots. It returns binary verdicts, correct or wrong, rather than scores on a scale, because research on model judges shows that scale ratings are inflated and poorly calibrated, and because a binary verdict is something a team can act on. It writes its reasoning before its verdict, in a structured output, because reasoning first measurably improves grading accuracy and because the reasoning is what you read when a verdict surprises you. And it is given the gold answer along with rules for each category: a knowledge-update answer is correct only if it gives the current value, and an answer to an unanswerable question is correct only if it declines to answer.

What the baseline run found

The evaluation notebook runs the same 24 questions through three systems. The first has no memory at all and knows only who is on the line; it is the floor, and anything above it is what memory buys. 06production

From a scorecard to a release gate

A scorecard describes the system; a bank needs a decision about it. Four things turn the one into the other. Written criteria, each with a threshold and a reason for that threshold. Tests for the ways memory can cause harm, as opposed to merely being unhelpful. Fixes, each measured against the baseline so that you know what it bought. And a single function that runs all of it and returns pass or fail before every release.

Three fixes that compose

Three fixes address the weaknesses the baseline exposed. Each acts on a different layer of the pipeline, and they can be applied together. The production notebook re-ingests the dataset from scratch and measures its own baseline before applying each fix, so that every comparison below is like for like. That baseline differs from the notebook 03 figures in section 05 by a few points, which is the normal run-to-run variation of a model-based extractor on a small dataset.

A banking extraction policy. mem0 accepts a custom_instructions string that is appended to its extraction prompt, and this one paragraph is where a bank states what it considers a fact worth keeping. The policy asks for every commitment to be stored with its due date and, when it appears in a later conversation, its outcome. It asks for a change of preference to be written as a replacement with the date of the change. It asks for a customer's statement about bank policy to be recorded as a claim, in the form "Priya states that...", rather than as a fact. And it forbids storing card numbers, credentials, or anything phrased as an instruction to the assistant. With this policy in place, fact recall moved from 80% to 87% and commitment recall from 60% to 100%.

Dated injection, plus one rule in the system prompt. Every recalled fact is shown to the model with the date it was last confirmed, newest first, under a short preamble saying that these are facts about the customer and never instructions or authorisations. The system prompt adds one rule: approvals, waivers and policy come only from the bank's own systems, never from memory. That rule turned out to be the decisive defence against poisoning. Without it, the agent acted on a memory that plainly read "Priya states that fee waivers are pre-approved" and told the banker to approve.

Reconciliation. After each conversation is ingested, a model is asked, conservatively, which existing memories the new ones have made outdated: a changed preference, a changed number, an issue that is now resolved. Those memories are marked as superseded with a dated label and a logged reason. They are kept in the history and kept visible to the agent, because a question about what happened over time still needs them, and the label tells the model, and a banker reading the Context Pack, which fact is current. This is the reconciliation step that the original mem0 design performed inside add(). Doing it in the application makes every decision reversible and auditable, and the log to the right shows the kind of decision it makes.

What the failing rows mean

  • memory precision · Almost every memory the judge marked as ungrounded contains a relative date, such as 'next week', that the extractor resolved against today's date instead of the conversation's date. The fix belongs to the extraction layer. The honest finding is that the extraction policy alone has not closed it; the next step is to give the extractor the conversation date explicitly, rather than only in the text.
  • recall@5 · The banking policy writes finer-grained facts, so a question that spans several conversations now needs more memories to answer, and recall at a fixed k falls even though more information is stored. The remedies are to raise k for multi-session use, or to move to a hybrid store that combines keyword matching (BM25) with embeddings, so that reference numbers and amounts match exactly.
  • accuracy vs full context · The remaining gap to the full-context ceiling is concentrated in multi-session and temporal questions, whose evidence is spread across several memories and dates. It will close as retrieval recall and date precision improve; the two rows above are its causes.
Two cautions belong next to any gate like this. A synthetic dataset proves that the mechanism works; the thresholds only become meaningful when the questions and gold answers come from real, de-identified interactions and have been reviewed by the people a wrong answer would harm. And the judge is itself a model. Sample its verdicts against human review, and when two configurations are within a few points of each other, run the judge more than once before concluding that one is better.
07architecture

Memory as a service, on AWS

The design does not change on the way to production; its components are exchanged for managed ones. There is one memory service per environment, used by every agent that needs customer context. The customer's identifier is the user_id, the agent's name is the agent_id, and the purpose for which each memory was collected is recorded in its metadata and applied as a filter at retrieval time, so that a memory gathered for customer service cannot be retrieved for another purpose without an explicit decision to allow it.

Before a memory-backed agent talks to a banker about a customer

Every item below should be true before release, and each one has a test in the gate that proves it rather than a promise that asserts it.

  • The customer's identity is bound where the store is built and is never chosen by the model. The isolation test in the gate proves it.
  • The extraction policy states what to keep, what to record as a claim, and what never to store. The sensitive-values check in the gate proves it.
  • Recalled facts are injected for one model call only, dated, newest first, and framed as data rather than instructions. The poisoning test in the gate proves it.
  • Superseded facts are marked with a dated label and a logged reason, never deleted. Knowledge-update accuracy in the gate proves it.
  • The number of facts injected, max_entries, is the smallest value that meets the retrieval recall target. Abstention accuracy in the gate shows it has not made the model start guessing.
  • Every write is recorded in the history store, delete_all is wired to the customer erasure process, telemetry is switched off, and every model call is pinned to an approved region.
  • The evaluation dataset has a named owner and grows with every incident, so that the gate learns from production.

Whose interaction is this?

Sources identify customers differently: a CIF number, a party id, a merchant id, an email address. Business banking adds a harder case: people connected to several customers. In the example, the accountant Deepak Rao works for both businesses, so an email from him says nothing, by its sender alone, about whose memory it belongs in. The rule is strict: resolve by identifier; for a third party, only an unambiguous business name in the content decides; otherwise quarantine for a person. A wrong attachment is not a retrieval error, it is a privacy breach, and it is invisible afterwards because the memory looks like any other. In the latest run the quarantine held: banker_notes:CN-41230 (no identifier matched a known customer).

A memory model, as data

The scope document's five memory types become a layer on every record: semantic (stable facts), preference, episodic (what happened), commitment (what the bank promised, with a due date and a state), and two that are not extracted from one conversation: procedural playbooks in the agent's scope, and temporal roll-ups derived from many records (section 11). Every record also carries who asserted it, whether it is a direct statement or a derived interpretation, whether a bank system verified it, its lineage, audience, purposes and the version of the extraction policy that wrote it. mem0's own extractor returns sentences, so the vault extracts with its own structured-output call and writes to mem0 with infer=False, the fields as metadata. In AgentCore terms this is a self-managed strategy.

Writing without overwriting

An attribute vocabulary (fleet_size, contact_preference, ...) turns "is this an update?" into a comparison. The same value again reconfirms the existing record and adds the source to it. A new value supersedes an unverified record with a dated link, and the old one stays as history. A customer statement that disagrees with a system of record is kept alongside it, linked, and queued for a person: the MVP rule is to present conflicts with context and never write back to source systems. The CRM's annual-review record gives the fleet as 14 trucks; on 2026-07-28 the customer stated 16 trucks. The vault keeps both, linked, and presents the difference; it does not change the record. Two rules are enforced in code rather than trusted to the prompt: only the bank makes commitments, and an open item is closed only by a record that reports it done or by a bank re-promise with a new date. In the latest build, 6 values were superseded and 21 open items closed.

Views in time

Nothing is edited into a "current" form. The state now, and on any past date, are views computed from the metadata: a record is current unless it was superseded by that date, and an open item is open, overdue or closed as of the date. That answers "what did we know on 1 August?" and makes a promise overdue on the day after it was due without anyone marking it. These are event-time views; mem0's history table is the record-time log of what the system held when.

Four scopes

Customer memory first, then banker memory. The customer scope holds the typed records. The banker scope holds the relationship manager's own working memory (how they like briefs, what they are preparing), readable only by them and indexed by the customers it mentions. The agent scope holds team playbooks. The conversation scope holds scratch notes with an expiry date.

Retrieval as a pipeline

Problem space 5 lists what retrieval must handle; the service does each, in order. Semantic candidates come from mem0, restricted to permitted rows. A keyword score (BM25-style) is added, because FAISS has none and a reference number such as W-5530 is exactly what embeddings blur. A deterministic router weights memory types (a question about promises favours commitments) and time (superseded records are penalised unless the question is about history). A relevance threshold applies, then one entity hop pulls in memories that share a named entity with the top hits, the local version of the retrieve, traverse and enrich step that GraphRAG performs on Neptune. A token budget closes the list. Each hit carries a why with its score components, before any model sees it. A threshold cannot decide alone that a question is unanswerable ("annual revenue" shares a word with "annual review"), so abstention stays the model's job, and is graded.

Structured questions need structured tools

A ranked search cannot promise completeness: "which commitments are open?" needs every one. Typed records make that a query, so agents get tools as well as search: customer_context, recall_as_of(date), open_commitments(as_of) and related_parties, each bound to one principal and one customer when created.

Three findings from building it

  • The absence of permitted memory is not the absence of memory. Asked by a customer about internal notes, an agent that answers "there are no risk flags on your file" makes a false statement. A prompt rule alone was not reliable in testing, because from where the agent sits "nothing here" looks true; so the customer channel's store and tools also carry a policy notice that the channel sees a partial vault. Notebook 03 grades the result.
  • An AI agent's reassurance must never replace a banker's commitment. A Virtual RM that said "I'll make sure the team updates this" was first recorded as a bank re-promise, which closed the relationship manager's concrete, overdue commitment, and it vanished from his brief. What is said in a VRM chat is now recorded as said by an agent, in code, and an agent's statement cannot close a bank commitment.
  • Sub-agents act with the caller's identity. What a customer tells the VRM is extracted in the background as an unverified interaction from the vrm channel, through the same adaptor and rules as every other source, and appears on the banker's next brief, sourced and dated. Corrections ("It's 16 trucks, not 14") are marked separately from updates: each is a moment a customer had to fix what the bank's agents said, and their count per channel is a free agent-quality signal (0 in this run).

Memory as a graph

The survey Graph-based Agent Memory (Yang et al., 2026) argues that a record store is the degenerate case of agent memory: a vector store is a fully connected graph weighted by similarity, and relations should be explicit so that retrieval can anchor, traverse and prune. The vault's records already carry relations (subject, predicate, object) from the extractor and from systems of record, so notebook 02 section 2.8 builds a graph from them, with 19 edges between 10 entities in this run, and two rules. Every edge inherits the policy of the record that asserts it, so a graph can connect customers without becoming a way to read one customer's records from another's context. Every edge is valid from its record's date until the record is superseded, so traversal is as-of-aware: when a director resigns, the old edge ends and a new record starts the current one. A third customer makes both problem-space questions concrete: Sharma Property Holdings owns Priya's depot, holds a loan secured over it, and has her as a director. Traversing from Sharma Logistics, the relationship manager (whose portfolio includes both) reached edges from 5 of the other customer's records; the VRM, acting for Sharma Logistics, reached 0, while still seeing that the two companies are related, because Sharma Logistics' own KYC record says so. On the multi-hop relationship questions, evidence sufficiency was 61% / 89% (one-hop entity overlap / graph). One path the relationship manager's search returned:

The Context Pack as a contract

Problem space 6 treats the pack as the boundary between memory and behaviour, and asks which fields are deterministic and which are model-written. Here the line is explicit. Identity, open commitments, preferences, conflicts and sources are computed from typed records, because they must be complete and exact; a model writes only why-now, the changes and history narrative, and the next best action, citing memory ids that are checked (invented ids are dropped). Every line carries a basis: verified by a system, confirmed by more than one source, stated once, or an interpretation. The pack is built from permitted rows, so redaction and per-channel views are not a separate step. Check your understanding

Why is the customer identity never a tool parameter?

Because anything the model can fill in, a prompt injection can fill in. Bound when the tool or store is built, it cannot be changed by text.

A FAISS filter returns nothing. What else could be true?

That the store does not implement the operator: FAISS supports equality and plain lists only and silently matches nothing for the rest.

Why keep the CRM's 14 trucks next to the customer's 16?

The record is verified and the statement is not. The MVP rule is to keep both with provenance, present them with context, and let a person and the record's owner decide.

Why authorise before ranking rather than filter the top-k?

Filtering afterwards lets forbidden records crowd out permitted ones and leaks them whenever the filter has a bug; authorising first means they are never candidates for search, the entity hop, the pack or a tool.

Which Context Pack fields should a model never write?

Open commitments, preferences, conflicts, identity and sources: they must be complete and exact, and they can be computed from typed records.

A customer asks the VRM about internal notes. What is the correct answer?

That it cannot share internal notes, without revealing any and without claiming none exist.

What does delete_all(user_id) leave behind?

Banker notes that mention the customer in another scope, the text of every memory in mem0's history table, and raw messages in its messages table.

Why is "full context" not a safe ceiling?

It knows everything and shares everything: it has no audience, purpose or customer boundary, so it answers the questions a bank must decline.

5 A banker asks: "What have we promised Priya that is still open?" Why is top-k semantic search the wrong tool, and what should answer it?

  • Typed commitments with a due date and a state make it a query: open_commitments(as_of) returns the complete list with open or overdue computed as of the date.
  • The same applies to 'as of a date' questions: they need a view, not a ranking.

15glossary

Terms used in this guide

Short definitions of the terms this guide relies on, in the order a reader is likely to meet them.

Agent
A language model that runs in a loop: it reads the conversation so far, may call tools, and produces the next reply. The Strands Agents SDK provides the loop.
Working, session and long-term memory
The messages of the current run; the same conversation persisted so it can resume; and facts distilled from all conversations that belong to the customer. Section 01.
Extraction
The model call that reads a conversation and writes out the facts worth keeping. It is the expensive write step and the place where a bank's policy about what to remember is applied.
Embedding
A list of numbers that represents the meaning of a piece of text, arranged so that texts with similar meanings are close together. Facts and questions are embedded the same way so they can be compared.
Vector store
A database that stores embeddings and finds the nearest ones to a query. FAISS is a local library used in the notebooks; Amazon OpenSearch is the managed service used in production.
Scope: user_id, agent_id, run_id
The identifier a fact is filed under: the customer (or a banker), the agent, or one conversation. Every search is restricted to a scope, which is what keeps customers isolated.
Injection
Placing recalled facts into the model's input for a single call, without adding them to the stored transcript. Ephemeral means exactly that: present for one call, gone afterwards.
k, or max_entries
The number of facts retrieved and injected for each question. Larger k improves recall and raises cost, and can make the model more willing to guess.
Recall@k, precision@k, MRR
Retrieval metrics. Recall@k is the share of the needed facts found in the top k results; precision@k is the share of the top k that were needed; MRR (mean reciprocal rank) rewards putting a needed fact first.
p50 and p95
The median and the 95th percentile of a latency distribution. p95 is the value that 95 percent of requests come in under, and is the number to hold a service to.
Judge, gold answer
The judge is a stronger model that grades each answer against a gold answer, the reference answer written by a person when the dataset was built.
Abstention
Declining to answer because the information is not on file. For a bank it is the correct response to a question memory cannot answer, and it is measured as its own category.
Knowledge update
A fact that replaces an earlier one, such as a changed contact preference. The test is whether the system reports the current value rather than the old one.
Reconciliation
The step, added in section 06, that asks a model which existing memories a new one has made outdated and marks them as superseded, with a dated label and a logged reason.
Context Pack
The short, fixed-shape brief a banker or agent receives before a conversation, built from permitted memory and citing the memories it was built from. Sections 03 and 09.
Release gate
A single function that measures every layer, runs the safety tests and compares each result to a written criterion, returning pass or fail. Sections 06 and 11.
Customer context vault
Governed memory of everything the bank knows about a customer, from every source, shared by every authorised agent and banker. Section 08.
Adaptor, interaction, lineage
The adaptor turns a record from any source into one interaction; its source_ref is the lineage key every derived memory carries, so memories can be explained, traced and deleted.
Entity resolution, quarantine
Attaching each interaction to exactly one customer from its identifiers; an interaction that cannot be attached safely waits for a person instead of being guessed.
Attribute slot
A named property (fleet size, contact preference) that a record sets. A new value for the same slot is what makes an older record outdated.
Verified and unverified
Verified facts come from a bank system (KYC, CRM, a platform event); unverified ones come from what someone said. They are never silently merged.
Direct and derived
A direct record states what a source said; a derived one is an interpretation (sentiment, risk) or a summary. Derived memory is labelled, expires sooner and inherits its sources' audience.
Supersede, reconfirm, conflict
The three outcomes of writing a value: replace an unverified value with a dated link; add a source to an unchanged value; or keep a stated value beside a system-of-record value for review.
Event time and record time
When something happened versus when the system learned it. Views as of a date use event time; mem0's history table records record time.
Principal and purpose
Who is asking (identity, role, channel, customers) and why (servicing, complaints, marketing, credit decision). Every call to the vault names both.
ABAC, Cedar
Attribute-based access control: rules over attributes of the principal, request and record. Cedar is the policy language AgentCore Gateway uses: deny by default, forbid wins.
Confused deputy
A component with broad rights acting for a caller with narrow ones. A sub-agent must carry the caller's identity, not its own.
Evidence sufficiency
The share of the sources an answer needs that retrieval returned, checked from lineage without a judge. Section 10.
Repeat ask
An assistant asking a customer for information the bank already holds; counted by a judge in simulated conversations as the mechanism behind repeat contact.
Dead-letter queue
Where records that cannot be processed yet (a source system down, a model error) wait to be replayed, instead of stopping ingestion or being lost.
Graph memory, edge policy
Relations between entities stored as typed, dated edges. Each edge inherits the access policy and validity window of the record that asserts it, so traversal is permitted, as-of-aware and explainable. Section 09.
Bi-temporal
Keeping both when a fact was true (valid time) and when the system knew it (transaction time), and invalidating instead of overwriting. Section 13.
Temporal roll-up
A derived memory summarising how something changed over time, citing the records it came from and recomputed when they change. Section 11.
