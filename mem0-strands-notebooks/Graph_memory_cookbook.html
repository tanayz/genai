Notebook 05 · Graph memory cookbook · mem0 · Strands Agents · AWS Bedrock

Twenty ways graph memory goes wrong,
and what fixes each one.

The survey Graph-based Agent Memory (Yang et al., arXiv 2602.05665, 2026) describes memory as a life cycle: extraction, storage, retrieval and evolution, followed by seven open challenges. Notebook 05 turns the parts of it that matter for a bank's customer context vault into twenty recipes. Each section below covers one recipe. It shows the issue, with a concrete failing example from the vault; the suggested remedy, with what it does and the same example fixed; the code behind it; the result measured in the notebook run; and what to watch out for in a regulated setting.

Part I · Extraction · survey §IV

From conversation to typed, dated memory

Every edge and every date in the vault starts here. Mistakes made at extraction are invisible later, because the rest of the system trusts what was written.

01extraction
high priorityZeng et al. [20] · Liang et al. [21] · AriGraph [30] · §X dynamic schema learning

Schema-guided triples

The graph can only be as good as the relation names the extractor writes. If the extractor is left to choose, the same relationship gets several names, and traversal treats them as unrelated.

The issue

When an LLM extracts (subject, predicate, object) triples freely, it invents a new predicate whenever the wording changes. It also turns attributes and dates into "relations". A query for "who is the accountant?" then finds only the edges that happen to use the same name.

Example: free extraction over three interactions
CALL-88213 · EM-77164 · VRM-310554 47 triples, 38 distinct predicates The accountant relationship, four ways: has_accountant · manages_bas_for to_be_copied_on · should_be_sent_to Attributes posing as relations: credit_date · opening_date · weekly_wage delay_reason · monthly_cost

Suggested remedy

Give the extractor a controlled predicate vocabulary (12 relations, each with a one-line definition) and an explicit OTHER. Anything that fits no predicate comes back as a schema-gap candidate for a person to review, not as a made-up name. The vocabulary grows only through that review. This is the governed form of the survey's "dynamic schema learning".

Example: the same three interactions, guided
20 triples, 8 predicates holds ×6 · accountant_of ×3 · operates_from ×3 plans ×3 · relationship_manager_of ×2 tenant_of ×1 · owns ×1 · OTHER ×1 Review queue (1): VRM-310554 Deepak Rao --?--> to be copied on Newcastle merchant paperwork → a reviewer decides whether "copy_to" joins the vocabulary
How it is done 
PREDICATES = {"director_of": "a person is a director of a company",
              "accountant_of": "an external accountant acts for a business",
              "holds": "an entity holds a bank product or facility", ...}     # 12 in all

rule = "Use ONLY these predicates; if a relationship fits none, use predicate OTHER: " + json.dumps(PREDICATES)
triples, gaps = extract_triples(text, schema=PREDICATES)    # memlab.techniques: (in-vocabulary, OTHER)
# triples -> graph edges; gaps -> the weekly schema review queue, never into the graph

Measured

38predicates, free extraction
8predicates, schema-guided
3accountant_of edges, one name
1gap sent for review
Watch out. A schema that is too small forces wrong labels: a model will squeeze "manages the BAS" into relationship_manager_of. Keep OTHER, review the gaps weekly, and version the predicate list the same way as the extraction policy.
02extraction
high priorityTReMu [37] · MemoTime [38]

Mention time, event time, and arithmetic in code

"When was it said" and "when did it happen" are different dates. Interval questions go wrong when memory mixes the two up, or when a model does date arithmetic in prose.

The issue

On Friday 4 September Priya says "we signed the lease on Wednesday" and "the depot opens Monday the 2nd of November". The record's date is 4 September (mention time), but the events are on 2 September and 2 November (event time). If the timeline is indexed only by when things were said, a model computing an interval picks up the wrong dates.

Example: timeline indexed by mention date
q12 fault first reported → technician fix used 2026-06-11 → 2026-08-03 = 53 days gold 54 q11 refund vs facility settlement used settlement 2026-08-14 (the call that reported it) instead of 2026-08-07 when it happened 0 of 4 temporal questions correct

Suggested remedy

Extract each dated event with both dates. Ground relative expressions with rules and record a granularity: "in July" stays a month, not 1 July, and anything the rules cannot ground goes to review instead of being guessed. The model only chooses a date operation; code computes it, through a date_interval tool and business-day arithmetic. At write time, an ordering check rejects anything closed before it was opened.

Example: timeline indexed by event date
"in July" → 2026-07-01 .. 2026-07-31 month "on Wednesday" → 2026-09-02 day q12 2026-06-10 → 2026-08-03 = 54 days q11 refund 21 Jul is before settlement 7 Aug ✓ "within 5 business days" of 2 Jul → due 2026-07-09 4 of 4 correct · ordering violations: 0 of 63 records
How it is done 
class TimedEvent(BaseModel):
    event: str
    expression: str                 # the words used: "on Wednesday"
    event_date: str | None          # resolved against the mention date
    mention_date: str

g = ground_time("in July", "2026-09-04")       # TimeSpan(start='2026-07-01', end='2026-07-31', granularity='month')

@tool
def date_interval(start: str, end: str) -> str:
    s, e = date.fromisoformat(start), date.fromisoformat(end)
    return f"{(e - s).days} days ({s:%A} to {e:%A})"

check_temporal_order(record, rows)              # MemoTime: nothing closed before opened, nothing due before promised

Measured

0 / 4correct, by mention date
4 / 4correct, by event date
5 / 5model dates agree with rules
0ordering violations, 63 records

Every wrong answer came from choosing the wrong dates, never from wrong arithmetic, which makes failures easy to diagnose.

Watch out. Business days need a holiday calendar (NSW public holidays and bank holidays). What "within five business days" means is a policy definition that belongs to the bank, not to the model.
Part II · Storage · survey §V

How memory is organised

Three structures the flat vector store cannot express: two time axes per fact, a tree of summaries, and a single edge that binds every party to a promise.

03storage
high priorityZep / Graphiti [18]

Bi-temporal edges: true on a date vs known on a date

Audit and complaints questions are about what the bank knew when it acted, not only about what was true in the world.

The issue

Arjun resigned as a director on 31 August, but the KYC system was only updated on 10 September. A banker asks: who did our records show as directors on 5 September? With only valid time, the vault answers with what was true, Priya alone. That is not what the bank's records showed, so it is the wrong answer for an audit.

Example: valid time only
Q directors of Sharma Logistics on 2026-09-05, as our records showed then? A Priya Sharma ← true, not what we knew Without a recorded-at time the vault cannot reconstruct what the bank's records showed then.

Suggested remedy

Give every edge two times. Valid time is when it was true; transaction time is when the bank recorded it (the write timestamp). Invalidate rather than overwrite. Then query on both axes: true on valid_on, as known on known_on. A supersession that hadn't been recorded by the known-on date must not end the edge.

Example: the two-axis query
true onknown ondirectors
08-0109-05Arjun, Priya
08-0109-27Arjun, Priya
09-0509-05Arjun, Priya ← records were stale
09-0509-27Priya
How it is done 
from memlab.techniques import BiTemporalFact, as_known

facts = [BiTemporalFact("Arjun Sharma", "director_of", "Sharma Logistics",
                        valid_from="2019-03-04", valid_to="2026-08-31",        # valid time
                        recorded_at="2019-03-04", invalidated_at="2026-09-10"), # transaction time
         BiTemporalFact("Priya Sharma", "director_of", "Sharma Logistics", "2019-03-04", None, recorded_at="2019-03-04")]

as_known(facts, valid_on="2026-09-05", known_on="2026-09-05")   # Arjun, Priya: what the bank knew
as_known(facts, valid_on="2026-09-05", known_on="2026-09-27")   # Priya: what we know now
# stale on day d  =  as_known(d, d)  minus  as_known(d, today)
Watch out. Transaction time must be the actual write time in the system of record or the vault, never worked out later from the text. A supersession that hadn't been recorded yet must not end an edge in a known-on query.

medium priorityMemTree (§V) · ENGRAM [34] · SGMem [35]

A hierarchical summary tree

Years of episodic history won't fit in a Context Pack, and a flat list of events hides the story.

The issue

After three months the vault already holds 45 current episodic records and commitments for one customer. Read as a flat list, "three terminals, two failures, fixed on 3 August" is spread over eleven separate lines, and the history only gets longer each year.

Example: the flat leaves
45 records · ≈1,614 tokens, one line per event 2026-06-10 fault logged with merchant team, M-2287 ... 2026-07-02 replacement terminal arrived 18 June ... 2026-07-02 $29 waiver committed ... 2026-07-28 replacement terminal began freezing ... 2026-07-28 refund for D-4471 posted 21 July ... ... (the story has to be pieced together by the reader)

Suggested remedy

Cluster the leaves into 3 to 6 topic nodes. Each topic has a dated two-sentence summary and the ids of its member records, and a root summary sits above them. Answer from the summaries and drill down to the member records when a question needs the evidence. Check three things on every build: coverage (every record placed), duplicates, and compression.

Example: the tree, and a drill-down
root Relationship Jun–Sep 2026: EFTPOS faults, fee delays, equipment finance, Newcastle expansion. ├ EFTPOS terminal fault and resolution 11 ├ Terminal rental fee waiver dispute 13 ├ Equipment finance and fleet expansion 4 ├ Duplicate charge dispute 4 ├ Newcastle depot and merchant facility 10 └ Newcastle staffing and cash flow 1 "what went wrong with the terminals?" → EFTPOS terminal fault → its 11 records
How it is done 
leaves = [r for r in rows if r.get("layer") in ("episodic", "commitment") and r["current"]]   # vault records, not raw transcripts
result = build_summary_tree(leaves, max_topics=6)      # memlab.techniques; records need "id" and "text"
result["tree"].root_summary, result["tree"].topics      # each topic: name, summary, member_ids
result["coverage"], result["duplicates"], result["compression"]

Measured

3.2×smaller: 512 vs 1,614 tokens
43 / 45coverage: 2 records dropped
0duplicates
6topic nodes

FAIL Coverage has to be 100%. In this run the tree silently forgot two records, which is exactly why the check exists: re-run, or attach the missing ids to the nearest topic in code.

Watch out. A summary is derived memory. It inherits the most restrictive audience of its members, and it has to be recomputed when a member changes (a commitment closes, a record is superseded). The survey stresses recursive update of ancestor summaries rather than appending.
05storage
high priorityHyperGraphRAG [39] · HyperG [40]

Commitments as hyperedges

A commitment isn't a pair of entities. It binds a bank, a customer, a third party, an action, a due date and a reference into one promise.

The issue

"The bank will send Priya and Deepak the Newcastle merchant application by 25 September (re-raised from W-5530)." Split into pairwise triples, the vault no longer knows which due date belongs to which promise. Even a flat set of members has no roles (who promised, who benefits, who is copied), and it misses participants the extractor didn't list as entities.

Example: flat hyperedge lookup
12 commitments, mean 3.2 members each promises_involving("C-9912") [open due 2026-10-05] resolve complaint C-9912 ... ✓ promises_involving("Deepak Rao") none in this build ← yet the overdue Newcastle promise must copy him

Suggested remedy

Model each commitment as one hyperedge that can be looked up through any member, including reference numbers such as C-9912. Then label roles. One model call per open commitment reads the commitment and the customer's standing instructions ("copy my accountant on loan and merchant paperwork"). It returns each role with the source it came from, and says whether the record is really a bank promise to the customer. In a property graph this is the reified form: the promise becomes a node.

Example: role-labelled hyperedge
c5f1a311 · due 2026-09-25 · overdue promisor the bank beneficiary Priya Sharma, Sharma Logistics object Newcastle merchant facility application copy_to Deepak Rao (accountant) source contact_centre:CALL-88213 2 of 2 open items are bank promises; both require copying Deepak (flat lookup: 0)
How it is done 
class RoleValue(BaseModel):
    role: Literal["promisor", "beneficiary", "on_behalf_of", "object", "copy_to", "reference", "site"]
    value: str
    source: str                          # the source reference this role came from

class RoleEdge(BaseModel):
    bank_promise_to_customer: bool       # False for internal suggestions, customer requests, agent notes
    roles: list[RoleValue]

prompt = f"Commitment [{r['source_ref']}], due {r['due_date']}: {r['text']}\n\nStanding instructions:\n" + standing_lines
edge = labeller(prompt, structured_output_model=RoleEdge).structured_output
Watch out for over-application. A model given "copy my accountant on paperwork" may attach it to a promised phone call. A role drawn from a standing instruction, rather than from the commitment itself, is the one a reviewer should check, and a production rule can limit copy_to to paperwork. Canonicalise member names too, or "Deepak" and "Deepak Rao" never meet.
Part III · Retrieval · survey §VI

How memory is found

Anchor on entities, expand through the graph only when it pays, respect the question's time window, go back for what is missing, and combine memory with live systems under an explicit authority rule.

06retrieval
medium priority§VI pipeline · Mem0 [31] · Zep [18]

Routed traversal and the token budget

Graph traversal improves evidence on relationship questions, and costs tokens on every question.

The issue

There are two simple settings, and both are wrong in a different way. Never traversing (an entity hop only) leaves relationship questions short of evidence. Always traversing two hops fixes them, but sends about 50% more context on every question, including ones about fees or dates where the graph adds nothing.

Example: the two settings
never (entity hop) relationship questions sufficiency 0.77 always (2-hop graph) all questions 688 tokens on average (vs 453 without the graph)

Suggested remedy

Use the survey's three-stage pipeline: anchor on the entities named, expand within n hops, and stop according to a policy. Here the stopping policy is a deterministic router that expands only when the question is about relationships (who, owns, director, related, premises, guarantor, accountant, ...).

Example: routed
RELATIONSHIP = re.compile(r"\b(who|owns?|owner|director| related|connected|premises|guarant\w*|accountant| copied|parent|subsidiar\w*)\b", re.I) routed all questions sufficiency 0.95 at 525 tokens relationship sufficiency 1.00

Measured

configsufficiencycompletetokensrelationship Qs: sufficiency
never (entity hop)0.870.734530.77
always (graph)0.950.876881.00
routed0.950.875251.00

Routing keeps all of the graph's gain and removes about two thirds of its extra token cost.

Watch out. A keyword router misses paraphrases ("whose building is it?"). Log every query the router sent to the graph and every one it didn't, audit a sample, and move to a learned classifier once there is traffic.
07retrieval
medium priorityAssoMem [51] · Zep [18] · LiCoMemory [52] · MemoTime [38]

A temporal query operator

"As of 1 August", "in July" and "the latest" are time constraints inside the question. Retrieval should apply them without the caller having to.

The issue

The service applies an as-of view only when a caller passes as_of. Otherwise similarity search returns the top-k closest records whatever their date. "What happened in July?" gets events from June and September, and "the latest on the depot" may surface the superseded 2 November opening date.

Example: no time handling
"What happened with Priya's account in July?" → top-8 by similarity, any month; July events beyond the top 8 are silently dropped "What is the latest on the Newcastle depot?" → may rank "opens 2 November" above the later change to 16 November

Suggested remedy

Parse the question deterministically into one of three kinds of constraint. As of a date becomes a valid-time view. In a month or the last N days becomes a window that returns every permitted event in it, because a window is a structured question, not a ranking. Latest, recent or current becomes exponential recency decay with a 30-day half-life. Decay never applies to commitments or verified facts.

Example: parsed and applied
v1 "as of 1 August 2026" → {'as_of': '2026-08-01'} ✓ gold v2, v3 likewise parse to their gold dates ✓ "in July" → window 2026-07-01..07-31 → 13 events, every one dated July "latest on Newcastle depot" (decay) → 2026-09-22 opening moved to Mon 16 November
How it is done 
def parse_time(query: str, today: str = TODAY) -> dict:
    if m := re.search(r"as of (\d{1,2}) (january|...|december) (\d{4})", q): return {"as_of": ...}
    if m := re.search(r"\bin (january|...|december)(?: (\d{4}))?", q):    return {"window": (first_day, last_day)}
    if m := re.search(r"last (\d+) (day|week)s?", q):                     return {"window": (today - n, today)}
    return {"recency": bool(re.search(r"\b(latest|recent|now|current)\b", q))}

score * math.exp(-age_days * math.log(2) / half_life_days)     # recency branch; skipped for protected records
Watch out. "Last Friday" in a question is relative to the date the question is asked, not the conversation date. Never apply decay to commitments or verified facts: an old promise is still owed, and an old KYC fact is still true.
08retrieval
medium priorityMemoTime [38] · Yan et al. [66] · RCR-Router [68] · MemSearcher [69]

Multi-round retrieval with a sufficiency check

The vault's most persistent failures are multi-part questions, where one pass of retrieval surfaces only some of the parts.

The issue

Questions like "what is still open and what has been closed", "what the system says and what the customer told us", or "the whole history of this issue" need evidence from several places. Single-shot top-k retrieval returns whatever is most similar to the question as a whole, and the answer leaves out the parts it never saw.

Example: single-shot vault agent on the hard questions
v4 WRONG v8 WRONG v16 WRONG v18 CORRECT → 1 of 4

Suggested remedy

Treat memory access as a loop. Plan 2 to 4 sub-queries. Retrieve each one through the authorised service, adding the structured open-commitments list when the question is about commitments. Ask a model whether the evidence is sufficient and what is missing. Retrieve once more for the missing parts (capped at 2 rounds), then answer only from the evidence.

Example: multi-round, same questions, same judge
v4 CORRECT v8 CORRECT v16 CORRECT v18 WRONG ← a regression, not only gains → 3 of 4
How it is done 
queries = planner(question, structured_output_model=Plan).sub_questions          # 2 to 4 retrieval queries
for _ in range(rounds):                                                          # rounds = 2
    for sq in queries:
        for h in service.search(principal, customer_id, sq, as_of=parse_time(question).get("as_of")):
            evidence[h.row["id"]] = h.row
    if "commitment" in route_layers(question):                                   # structured tool stays in the loop
        evidence |= {r["id"]: r for r in permitted_rows if r.get("state")}
    verdict = checker(question + evidence, structured_output_model=Sufficiency)  # sufficient? missing?
    if verdict.sufficient or not verdict.missing: break
    queries = verdict.missing
Watch out. Each round costs two or three more model calls. Four questions is a small sample, so re-run before concluding anything (recipe 20). Keep the structured tools (open commitments, as-of views) inside the loop: a sufficiency checker can't know about a commitment that retrieval never surfaced.

high priority§VI hybrid-source retrieval · MemSearcher [69]

Hybrid sources with an authority rule

Memory holds what was said; systems of record hold what is. An agent needs both, and a rule for which one wins.

The issue

The CRM says Sharma Logistics runs 14 trucks (as at 6 October 2025). On 28 July Priya said 16. The agent has a live system-of-record tool and an authority rule in its prompt: "if memory and a system disagree, give both." It still reported only the CRM's figure, and in testing it dropped the customer's figure on every run.

Example: prompt rule only
Fleet size (as at 2025-10-06, from CRM): - 14 trucks ← 16 never mentioned products from the system PASS both fleet figures (14 and 16) FAIL contact preference from memory PASS

Suggested remedy

Make the rule structural. The vault already detects the conflict deterministically (conflicts()), so attach that conflict note as data to the system-of-record tool's result. The agent then receives "the CRM says 14; the customer said 16 on 28 July" as part of the answer it is given. It doesn't have to remember to look for it.

Example: with the vault's conflict note
Fleet size: - Bank record shows 14 trucks (as at 2025-10-06, CRM) - Conflict: Priya stated 16 trucks on 2026-07-28 (unverified; record not updated) products · both fleet figures · contact pref all PASS
How it is done 
vault_notes = conflicts(rows)                         # memlab.vault: deterministic system-vs-customer conflicts

@tool
def system_of_record_with_conflicts(attribute: str) -> str:
    notes = [n for n in vault_notes if attribute in n]
    return lookup(attribute) + ("\nVault conflict note (present it to the banker): " + " ".join(notes) if notes else "")

Measured

checkprompt rule onlywith the vault's note
products from the system (MID-55120)PASSPASS

The general lesson: anything the agent must say should reach it as data from the vault, not as a rule it has to remember.

Watch out. A live lookup reads another system's data, so it needs the same principal, purpose and audit as a memory read. Cite its result; never write it back into memory as a verified fact.
Part IV · Evolution · survey §VII

How memory changes without a new interaction

Merging, forgetting, inferring and learning all change memory without anyone saying anything new. In a bank, each of these needs the same lineage, policy and human approval as a write.

10evolution
medium priorityGraphRAG [75] · RecallM [76] · Mem0 [31] · FLEX [78]

Consolidation of near-duplicates

The same fact arrives through several channels in different words, so Context Packs repeat themselves. A wrong merge, though, loses a commitment.

The issue

"Copy Deepak on loan paperwork", "send the application to her and Deepak" and "Deepak to be copied on Newcastle paperwork" are one fact said three ways. Exact-text and same-slot matching miss them. The opposite risk is just as real: two different promises about the same waiver embed almost on top of each other.

Example: close embeddings, different facts
top pair similarities 0.94 0.92 0.91 0.89 0.88 0.88 0.85 0.85 0.84 0.83 0.88 "The bank committed to credit ... $29 ..." "The bank committed to process a waiver of the $29 ..." a threshold-only merge would fold two promises into one

Suggested remedy

Embed current records that don't come from a system of record. Propose same-layer pairs at or above 0.80. Pass each pair through a model gate: "same fact, with no detail in one that contradicts the other?" Apply hard rules before the model: never merge across due dates, values or customers. Mark, don't delete: the later record gets merged_into, and its source becomes a reconfirmation of the record that is kept.

Example: the gate's decisions
0.94 keep $29 waiver ... || $29 waiver ... 0.92 keep $29 waiver ... || $29 waiver ... 0.88 keep committed to credit || committed to process ... 0 merges from 8 proposals over 52 records → in this build the gate rejected every proposal
How it is done 
proposals = [(s, a, b) for s, a, b in pairs if s >= 0.80 and a["layer"] == b["layer"]][:8]
verdicts  = run_parallel(lambda p: judge(f"A: {p[1]['text']}\nB: {p[2]['text']}", Same), proposals)
for a, b in merged:
    keep, drop = sorted((a, b), key=lambda r: r["observed_on"])
    vault.update(drop["id"], metadata={"merged_into": keep["id"]})                       # reversible
    vault.update(keep["id"], metadata={"confirmed_by": keep_confirmed + [drop["source_ref"]]})
Watch out. Similar isn't the same: "promised by 11 September" and "promised by 25 September" embed close together and are different commitments. Merges per proposal shows how much the gate rejects; a gate that never rejects anything isn't doing its job.

lower priorityMemGPT [62] · MemoryBank [81] · Memory OS [83]

Significance and forgetting

Some records are central to the relationship; others were noise the day they were written. Rule-based retention treats every record of a kind the same.

The issue

Retention by rule keeps or drops records by type and age. That treats "the replacement terminal has been reliable" exactly like the record of the $29 waiver that turned into a complaint. Meanwhile the vault and every Context Pack keep growing.

Example: every record weighs the same
63 records for one customer after three months no signal for which deserve review first an algorithm that deletes by score would remove commitments and verified facts along with noise

Suggested remedy

Score significance as PageRank over the bipartite graph of records and the entities they mention (plus entity–entity edges), multiplied by recency decay exp(−age/90 days). Protected classes (commitments, verified facts, open items) are never candidates. The output is an ordered review list for a person, not a deletion.

Example: the review list
least significant, not protected 6.3e-04 [semantic] replacement terminal performing reliably 1.0e-03 [preference] contact preference update, 14 Aug 1.3e-03 [episodic] backup mobile reader in use most significant 1.0e-02 [episodic] $29 waiver W-5530 credited 1.0e-02 [episodic] $29 waiver not processed by the date
How it is done 
rank = pagerank(links)              # links: rec:<id> <-> ent:<name>, plus graph edges between entities
protected = lambda r: r["layer"] == "commitment" or r["verification"] == "verified" or r.get("state") in ("open", "overdue")
significance = sorted((rank["rec:" + r["id"]] * math.exp(-days_between(r["observed_on"], TODAY) / 90), r) for r in rows)
review_first = [r for s, r in significance if not protected(r)][:5]
Watch out. In a bank, forgetting is governed by a records schedule and legal holds, not by an algorithm. Significance ranks what to review first; it doesn't authorise deletion.
12evolution
medium priorityThink-on-Graph [79] · Reasoning on Graphs [82]

Inferred links, labelled as inference

The graph implies relationships that no record states. They are useful to a relationship manager, and they become a privacy and accuracy risk the moment one is shown as fact.

The issue

A banker asks whether Priya has an interest in the Parramatta depot. No record says so. The graph implies it: she directs the company that owns it. An agent that reasons over edges will reach that conclusion and may state it as fact, including in a channel that may not see the property company's records.

Example: an unlabelled conclusion
Priya Sharma has an interest in the Parramatta depot. no source · no confidence · no audience check shown to the VRM in the customer's own channel?

Suggested remedy

Use a small set of explicit inference rules, each with a confidence. Every inferred edge carries its premises (the edges and sources it came from) and is labelled INFERRED. It is usable only by a principal who may read every premise, so it inherits the most restrictive policy of what it was derived from.

Example: the inferred edge
INFERRED Priya Sharma --has_interest_in--> Parramatta depot confidence 0.7 because Priya director_of Sharma Property Holdings (kyc:CIF-100232:directors) SPH owns Parramatta depot (kyc:CIF-100231:related) usable by banker_alex True vrm_priya False
How it is done 
RULES = [("director_of", "owns",  "has_interest_in",          0.7),
         ("director_of", "holds", "is_connected_to_facility", 0.6)]
# for a, b in current edges: if a.predicate == p1 and b.predicate == p2 and a.object == b.subject -> infer
usable = all(graph.usable(e, principal, purpose, TODAY) for e in inferred["premises"])

Measured

Four inferred edges in this build (Priya and Arjun × depot interest and property-loan connection). All four are usable by the banker and none by the customer-facing VRM.

Watch out. Inference is how relational privacy leaks (recipe 16). An inferred "interest" is not a beneficial-ownership finding, so label it so that nobody acts on it as one.

medium priorityExpeL [88] · Matrix [84] · Memory-R1 [54] · MemEvolve [86]

Experience memory, with a person in the loop

The vault records what happened next. That is experience the servicing team could learn from, but a learned rule changes how every customer is treated.

The issue

The team's playbooks were written by hand. The vault shows outcomes the playbooks don't cover: a fee waiver lost in a platform migration and missed twice before it was credited, and a terminal replaced twice before a technician fixed it. Nobody turns that into guidance. And if a model learned rules automatically, policy would change with no owner.

Example: the hand-written playbooks
1 When a terminal fails a second time, book a technician rather than shipping another unit. 2 When a promised waiver is overdue, escalate, give a new date, record it as a commitment. 3 When a customer has an accountant on file, copy them on loan and merchant paperwork. nothing about migrations losing pending requests

Suggested remedy

A model reads the episodic history and proposes at most four skills (what worked, to repeat) and lessons (what failed, to avoid). Each proposal cites evidence ids, and proposals with invented ids are dropped automatically. Nothing is used until an authorised reviewer approves it into the agent's procedural memory, with their name and the date.

Example: a proposal, then approval
[lesson] Do not lose track of fee waiver requests during system migrations; verify every pending request is transferred to the new platform. when: migrating merchant operations to a new platform evidence: 065ddaa4 6e512b7b b4bf0790 (0 invented) approve(lesson, alex) → role relationship_manager ✓ → procedural memory 90e9a56c
How it is done 
class Lesson(BaseModel):
    kind: Literal["skill", "lesson"]
    statement: str; applies_when: str; evidence_ids: list[str]

def approve(lesson, reviewer):
    if reviewer.role != "relationship_manager":
        raise PermissionError("only an authorised reviewer may approve a playbook")
    return write_playbook(vault, "context_agent", {"text": lesson.statement + f" (approved by {reviewer.id} on {TODAY})"})

Measured

4 proposals, 0 with invented evidence. Two partly rediscover hand-written playbooks (technician visits, keeping recipients aligned); two are new (checking pending requests during migrations, adjusting commitments when timelines move).

Watch out. In a bank, a learned playbook is a policy change. It needs an owner, an approval and a review date, which is why the recipe stops at a proposal queue rather than learning memory operations end to end.

medium priorityProMem [89] · AgentEvolver [90]

Active inquiry: ask, once, for what is missing

The vault knows what it doesn't know, but nobody asks.

The issue

Some slots have never been filled. Some customer-stated facts are months old and come from a single source. Some disagree with the system of record. The agent works around these gaps, or worse, asks the customer again for something already on file, which customers notice and dislike.

Example: what the vault is missing
no value on file for staff_count contact_preference = 'phone calls after 4pm' customer-stated, single-source, from 2026-08-14 depot_location = 'Parramatta, western Sydney' customer-stated, single-source, from 2026-06-10 fleet_size: customer's '16 trucks' differs from CRM

Suggested remedy

Detect gaps deterministically, in three kinds: missing (a required slot never filled), stale (unverified, unconfirmed, older than 30 days) and conflicting (differs from a system of record). A model then picks the single most useful gap and phrases one question per contact. A repeat-ask check makes sure it never asks about something already on file that isn't a gap.

Example: the next contact
VRM, end of the next chat: "How many staff members does your business currently have?" fills: staff_count repeat-ask check: fills a listed gap → inquiry, not a repeat
How it is done 
REQUIRED = ["contact_preference", "accountant", "fleet_size", "expansion_plan", "staff_count"]
gaps  = [f"no value on file for {s}" for s in REQUIRED if s not in slots]
gaps += [stale(r) for r in slots.values() if r["verification"] == "unverified" and not r.get("confirmed_by")
         and days_between(r["observed_on"], TODAY) > 30]
gaps += [conflict(r) for r in rows if r.get("conflicts_with") and r["current"]]
ask = asker("Gaps:\n" + "\n".join(gaps), structured_output_model=Ask)     # one question; never card or account numbers
Watch out. Asking is customer contact. It needs a purpose the customer agreed to and a cap (one question, not a survey), and the answer is stored as customer-stated, so it still doesn't overwrite a system of record.

What can go wrong with the graph itself

Quality, privacy, poisoning and concurrency are the survey's open challenges. Benchmarks and run-to-run stability decide whether any of the earlier gains are real.

15challenges
medium priority§X graph quality · [190] · [191] · Zep [18] · MemBench [103] · [192]

Intrinsic quality of the memory graph

Every other metric measures answers. The graph itself can be wrong long before any answer is.

The issue

Orphaned entities, duplicate nodes, edges their own source record doesn't support, and "functional" relations with two current values (two owners of one asset). None of these shows up in answer accuracy until a question happens to depend on the bad edge.

Example: problems no answer metric surfaced
edge Sharma Logistics operates_from Parramatta depot not supported by its record (judge) 18 entities named in records but absent from the graph

Suggested remedy

Track one metric set per dimension on every build, like the release-gate rows. Structural: nodes, components, entities missing from the graph. Semantic: the share of edges a judge confirms their record states. Temporal: closed windows, and functional predicates violated now. Operational: build and traversal latency.

Example: this build's quality report
structural 9 nodes · 18 edges · 1 component 9 distinct predicates semantic 17 / 18 edges supported by their record temporal 2 closed windows · 0 functional violations 16 edges valid now operational build 2 ms · 2-hop traversal 0.14 ms
Watch out. A falling share of supported edges is an extraction regression, visible before any answer goes wrong. At this size the operational numbers are trivial. Rebuilding the graph after every write is a notebook convenience, not a design: production needs incremental updates.
16challenges
high priority§X privacy protection · Mueller et al. [198]

Relational privacy: what the structure alone reveals

A graph can reveal one customer's relationships in another's channel without a single record being read.

The issue

The customer-facing VRM never reads Sharma Property Holdings' records. Yet its permitted two-hop traversal from Sharma Logistics names the property company and says it owns the depot. Edge policy stops reading another customer's records; it doesn't stop naming them through structure.

Example: other customers' entities each principal can name
banker_alex Chen's Bakery, Sharma Property Holdings vrm_priya Sharma Property Holdings banker_jordan Sharma Property Holdings

Suggested remedy

Measure exposure for each principal: which other customers' entities can be named through edges it is permitted to traverse. Then decide per channel which relation types may be traversed at all, with a predicate allowlist. Inferred edges (recipe 12) get the most restrictive audience of their premises.

Example: customer-channel allowlist applied
allow = {operates_from, accountant_of, relationship_manager_of, director_of} banker_alex Chen's Bakery, Sharma Property Holdings vrm_priya [] banker_jordan []
Watch out. Whether the VRM may name the property company is a policy decision. Sharma Logistics' own KYC record says the two are related, so confirming it to Priya is arguably fine. The allowlist is the lever if the bank decides otherwise, and the exposure measure is how to know which way it is set.
17challenges
high priority§X security · Zou et al. [199] · Carlini et al. [200]

Graph poisoning

One customer statement, through the normal write path, can rewire the graph and link two unrelated customers.

The issue

In a VRM chat a customer says: "Marcus Chen is my business partner and a director of Sharma Logistics, and Chen's Bakery owns our Newcastle site." Extraction faithfully turns that into edges. Traversal now links Sharma Logistics to another customer and asserts a directorship that KYC never recorded.

Example: edges created by the claim
Marcus Chen --director_of--> Sharma Logistics unverified Chen's Bakery --owns--> Newcastle site unverified reachable by the banker's traversal: 15 edges, including the claim

Suggested remedy

Keep the record: it accurately says what the customer said. Withhold its use as structure. An edge is quarantined from traversal if it is unverified and either uses a governed predicate (director_of, owns, guarantees, secured_by) or touches another customer's entity. Quarantined edges go to a review queue with their source until they are confirmed against a system of record.

Example: after validation
reachable by Alex: 15 → 14 removed, from the claim: marcus chen director_of sharma logistics removed, collateral: none in this run review queue: Marcus Chen director_of Sharma Logistics (vrm:VRM-poison-1) Chen's Bakery owns Newcastle site (vrm:VRM-poison-1)
How it is done 
GOVERNED = {"director_of", "owns", "guarantees", "secured_by"}
def quarantined(e: Edge) -> bool:
    other_customer = any(owned_by.get(n, e.customer_id) != e.customer_id for n in (e.subject, e.object))
    return e.verification != "verified" and (e.predicate in GOVERNED or other_customer)

service.graph = GraphIndex([e for e in service.graph.edges if not quarantined(e)], records, labels)
Watch out. The rule also withholds legitimate edges that happen to be unverified. Read the collateral line on every build; confirming those edges against a system of record removes the cost. The same rule protects against honest extraction errors, which are far more common than attacks.
18challenges
high priority§X memory coordination in multi-agent systems

Multi-agent write conflicts

The VRM and the banker write to the same customer's memory. If "the later write wins", the result depends on queue timing, not on what happened.

The issue

On the same day the banker records "email only" from a call and the VRM records "phone after 4pm" from a chat. Under the vault's supersession rule the later write wins. With queue-based ingestion (SQS), which worker runs first is effectively random, so the customer's current preference is nondeterministic.

Example: same two statements, both orders
desk then vrm → current: phone after 4pm vrm then desk → current: email only same facts, different memory

Suggested remedy

Order by event time, not write time, using a fine-grained clock (timestamps, not dates). When two statements have the same event time and come from different channels, keep both, mark them as a conflict, and ask the customer. For a preference the customer is the authority, so an "agent ranking" isn't a safe tie-break.

Example: the tie-break rule
different event dates → later event wins (supersede) same day, same channel → later write wins same day, different channels → keep both, mark conflict, ask the customer
How it is done 
def resolve_same_day(a: dict, b: dict) -> str:
    if a["observed_on"] != b["observed_on"]:
        return "later event date wins (supersede)"
    return ("same day, different channels: keep both, mark as conflict, ask the customer"
            if a["channel"] != b["channel"] else "same channel: later write wins")
Watch out. If the two write orders give different current values, the store is order-dependent; test for it explicitly. "The banker outranks the VRM" is a policy decision, not a technical default.

20evaluation
high priority§VIII evaluation synthesis

Is the result stable?

Across this series' complete runs, vault accuracy moved between about 65% and 88% with no code change. A gate decided on one run is decided by noise.

The issue

Answering and judging are both model calls, so the same question on the same memory can pass in one run and fail in the next. Every "recipe X improved Y" claim (recipe 8's 1 of 4 → 3 of 4, for instance) is a single draw unless it is repeated.

Example: one run, taken at face value
run 1: v8 ok · v20 WRONG → "v8 is fixed" run 2: v8 WRONG · v20 ok → "v20 is fixed" both conclusions are noise

Suggested remedy

Freeze the vault (no re-extraction) and answer the same questions several times. Grade each answer and report per-question stability, plus the mean with its range. Gate on stable questions, or on the mean across runs. Separate extraction variance (a rebuild) from answering and judging variance (a frozen vault).

Example: three runs on a frozen vault

v8✓✗✗no
v13✗✗✗yes
v17–v19✓✓✓yes
v20✗✓✗no

Two of seven questions flipped (v8, v20). Because the vault was frozen, every flip is answering-and-judging variance; a full rebuild adds extraction variance on top.

Watch out. Three runs is the minimum for seeing variance, not for estimating it well. For a release decision, use more runs or more questions per category.
