# Instructions: building the agent memory graph on real bank memory

You are continuing work on this repository on a machine inside a bank, where real agent memory and customer data are available. The repository was built and tested only on **synthetic data**: three fictional business customers, Sharma Logistics and two others. Your job is to carry its design over to the bank's real memory. You will build a governed customer context vault with a memory graph, and you will measure it with the same evaluation and release gates.

Read this file first, then `README.md`, then `docs/memory_graph_pipeline.md`. If you rename this file to `CLAUDE.md`, Claude Code loads it automatically in every session.

## 1. Rules for real data (these override everything else)

This repository was built on fictional data. The data on this machine belongs to real customers. When a rule here conflicts with speed or convenience, the rule wins. If you are unsure, stop and ask the person you are working with.

1. **Keep the data where it is.** Don't copy real records, extracts or embeddings to any location, service, URL, paste site, package index or repository outside the bank's approved environment. Call only the model endpoints and stores the bank has approved. Confirm the list with the person before your first call (see section 8).
2. **Read-only by default.** Treat existing memory stores, systems of record and shared databases as read-only. Get explicit approval for each change before you write, delete, re-index, migrate a schema, or run an erasure against anything shared. A previous approval doesn't carry over to the next change. Build into new, separately named collections that you created.
3. **Use the smallest data set that works, and prefer de-identified data.** Develop against a de-identified or sampled extract when one exists. Ask for real identifiers only when a step truly needs them, such as entity resolution against the real party directory.
4. **Keep customer data out of your replies and files.** Don't quote real customer details in your messages, in code comments, in docstrings, in test fixtures or in markdown. Report measurements as counts and rates, and refer to examples by record id. Never add real records to `data/*.json`. That folder stays synthetic so the teaching notebooks remain publishable.
5. **Never store sensitive values.** Card numbers, expiry dates, security codes, BSB and account numbers, passwords and one-time codes stay out of memory text, `metadata`, and both of mem0's SQLite tables: `history` (old and new text of every change, including deletes) and `messages` (a rolling window of raw messages per scope). The card-number check that ignores false alarms (Luhn checksum, not part of a longer token) lives in notebook 04, §2.7 (`luhn` and `CARD` in `tools/generate_nb04.py`). Move it into `memlab` and run it on every table before anyone else sees a build.
6. **Don't commit or push real data.** Make sure `.gitignore` covers `.mem0_data/`, any extracts, `results/` from runs on real data, and notebooks with outputs from real data, before you create anything. Commit or push only when asked.
7. **Respect retention and erasure.** Erasure must reach the vector store, `history`, `messages` and any graph store. The test in notebook 04, Part 2 (erasure residue = 0) is the minimum standard. Apply the bank's retention schedule; don't invent one.
8. **Report honestly.** If a gate fails, a run errors or a step was skipped, say so with the numbers. Synthetic results don't predict results on real data, so don't quote them as if they do.

## 3. Design rules to keep

The synthetic work established each of these by finding a failure and fixing it. Keep them all when you adapt the code. If one seems wrong for the real data, raise it with the person rather than dropping it quietly.

| Rule | Where it lives | Why |
|---|---|---|
| Every record carries lineage (`source_ref` = system:native id) and the policy version that extracted it | `vault._meta`, `POLICY_VERSION` | deletion, erasure, re-extraction and citations all depend on it |
| Unresolved or ambiguous customers are quarantined, never guessed | `vault.resolve_customer` | one wrong merge discloses one customer's data to another |
| Supersede, never overwrite; history is queryable as of any date | `vault.write_record`, `vault.view` | audit and complaints ask what was true, and when |
| Customer statements that conflict with a system of record are kept as conflicts; the system of record is authoritative and the conflict is delivered **as data** | `vault.conflicts`, `techniques.resolve_by_authority` | a prompt rule alone failed on every run; the conflict note delivered as data passed |
| An AI agent cannot close a commitment a banker made; extractions keep `asserted_by` | `vault.apply_guards`, `vault.may_close` | an assistant re-stating a promise once closed the banker's real commitment |
| Authorise before ranking; nothing unauthorised enters the candidate set | `access.MemoryService.search`, `access.authorize` | filtering after ranking leaks through scores, counts and summaries |
| Graph edges inherit the asserting record's policy and validity window | `graph.GraphIndex`, `graph.graph_records` | a graph can reveal another customer through its structure alone (cookbook recipe 16) |
| Customer-facing roles see a withheld notice, never a false denial | `access.WITHHELD_NOTICE` | "we have no record" is false when records are withheld |
| Unverified claims about relationships go to review, not into the graph | `techniques.quarantine`, cookbook recipe 17 | memory poisoning: one chat statement can create a director edge |
| Time has two axes: valid time (true on) and recorded time (known on) | `techniques.BiTemporalFact`, `as_known` | "what did our records show on 5 September" differs from "who was a director on 5 September" |

### mem0 and FAISS traps already found
- FAISS supports only exact values and plain lists in filters. Operators such as `{"in": [...]}` or `{"gte": ...}` **silently match nothing**. Check each filter operator against the vector store you use in production.
- mem0 2.x: `search()` and `get_all()` take `filters={"user_id": ...}`. `add()` only adds, so supersession is your code's job. There is no timestamp parameter, so put event dates in the text and metadata.
- Lexical scores must saturate (`s/(s+3)`). Normalising by the maximum score makes any relevance threshold meaningless. `MemoryService(min_score=0.30)`.

## 4. Plan of work

Work in phases. Each phase ends with a measured result written to `results/` (git-ignored on this machine) and a short note to the person. Don't start a phase that writes to anything shared until they have agreed to the target store.

### Phase 0: Inventory (read-only, about 1–2 days)
- Find out what "agent memory" means here: which stores (vector store, database, CRM notes, transcripts, case systems), which schemas and volumes, how far back the history goes, and who owns each.
- For each source, map its fields to `vault.Interaction`: `source_system`, `native_id`, `customer_ref`, `occurred_at`, `channel`, `participants`, `text`, `audience`.
- Map existing access rules to `access.Rule` (role, purpose, audience, action).
- Write `docs/real_data_mapping.md`. Include field mappings, gaps, data-quality problems found and open questions, but no customer data.

### Phase 1: Adaptors and entity resolution
- Write one adaptor per source in the style of `vault.ADAPTER_RULES`. Each must be idempotent on `native_id`, keep lineage, and send any record it can't parse to a dead-letter queue (notebook 04, §2.1).
- Point `resolve_customer` at the real party directory. Measure the resolution error rate on a sample a person has labelled, and send anything ambiguous to quarantine.
- **Done when:** a re-run is idempotent, every record has lineage, the resolution error rate is measured, and quarantine has an owner who works through it.

### Phase 2: Typed extraction and the graph
- Version a copy of `EXTRACTION_POLICY` for the bank's own vocabulary: products, relationship types, commitment language. Every change produces a new `POLICY_VERSION`. Re-extraction by version is in notebook 04, Part 2.
- Replace `techniques.PREDICATES` with the bank's relationship schema, agreed with the person (cookbook recipe 1).
- Build edges with `GraphIndex` semantics. Add a recorded-at time to every record and edge (bi-temporal, recipe 3).
- Choose the production graph and vector stores with the person, for example Neptune or OpenSearch. Re-test the filter semantics (section 3) on whatever you choose.
- **Expect variance between builds.** In the synthetic runs, the same standing instruction ("copy my accountant on loan paperwork") was typed as a `preference` in one build and a `semantic` fact in the next. Code that reads the vault must not depend on one exact layer label.

### Phase 3: Retrieval and the Context Pack
- Route every read through `MemoryService` (policy first), and add the graph with `enable_graph()`.
- Add routed traversal (`route_to_graph`), a temporal operator (`parse_time_query`), multi-round retrieval for multi-part questions (`multi_round_retrieve`), and code-side date arithmetic (`answer_temporal`, `days_between`, `add_business_days`).
- Replace `NSW_2026_HOLIDAYS` with the bank's holiday calendar for each jurisdiction. "Five business days" is a bank policy definition, not the model's.
- Index timelines by **event date, not mention date**. On the synthetic temporal questions this made the difference between 0 of 4 and 4 of 4 correct (cookbook recipe 2).

### Phase 4: Evaluation and gates on real data
- Build a real gold set **with people**: questions, gold answers, supporting record ids, and boundary probes (questions whose correct answer is "withheld"). Store it inside the approved environment, never in `data/`.
- Re-use the four levels from notebook 03 (memory, retrieval, Context Pack, agent) and the vault gate from notebook 04, Part 2. Who sets the thresholds and who signs off a release are decisions for the person, not for you.
- Run every model-judged gate **three times and decide on the mean**. On synthetic data, one stability check scored 57%, 71% and 86% across three runs, and individual verdicts flipped (cookbook recipe 20).
- Agree on any judge change against a sample people have labelled before relying on it.

### Phase 5: Evolution (only with human review)
Consolidation (`propose_merges` then `gate_merge`), significance, inferred links (`infer_links`, always labelled as inferred), lessons from experience (`propose_lessons`), and active inquiry (`find_gaps` then `phrase_inquiry`). Every one of these *proposes*; a person approves before any agent uses the result.

The cookbook (`05_graph_memory_cookbook.ipynb`) marks each technique by its importance for a bank's customer context vault. Start with the 🔴 ones. In these areas a mistake becomes a privacy, regulatory or customer-harm incident rather than a weaker answer.

## 7. How to work

- **Check before you claim.** Run the code and read the output. For notebook changes, regenerate them and confirm each cell matches its generator. Run `python -m doctest memlab/techniques.py` after touching `techniques.py`.
- **Work in small, measured steps.** Wrap new utilities in `@timed(kind)` so `latency_report()` covers them, and add each one to `docs/memory_graph_pipeline.md` with its source, its purpose and its latency.
- **Keep model calls bounded.** Use `run_parallel` with a small worker count (4–6) and `with_retry`. The Bedrock quotas on this account may be lower than in the synthetic setup.
- **Long runs:** `tools/run_all.py` re-executes itself under `caffeinate` on macOS. On other systems, use `nohup` or the platform's equivalent. Use `--from NN` to resume after a failure.
- **Match the code's style:** plain prose comments that say why, type hints, pydantic models for structured model output (`agent(prompt, structured_output_model=Model)`), no mocking of models in evaluations.
- **Name sources properly:** when you add a technique from a paper, credit the paper and say what it contributed, as the cookbook does for each recipe.
